
## Rules

1. **Never push to `main` or `dev`.** Every change reaches `dev` through a pull request (GitLab calls it a merge request).
2. **Start every branch from the latest `dev`.** Pull `dev` first, then branch from it.
3. **Name branches `ft/<topic>` or `hotfix/<topic>`, nothing else.**
   - `ft/` adds or changes a feature. `hotfix/` corrects something that is broken.
   - The topic is short, lowercase and hyphenated: `ft/login-endpoints`, `hotfix/otp-expiry`.

5. **Write commits and pull requests in the formats below.**

7. **Open a merge request only when Abdulaziz says so.** A pushed branch alone is fine.

## Commit message

A 1–4 sentence summary, then the **Features:** and **Fixes:** bullets.

```text
<1–4 sentences: what this commit does and why.>

**Features:**
- <plain-language bullet>

**Fixes:**
- <plain-language bullet>
```

Git shows the summary paragraph as the commit's title (for example in `git log --oneline`), so keep the sentences short and put the most important one first.

## Pull request

**Title:** `Merging <source> into <target>`, for example `Merging ft/login-endpoints into dev`.

**Body:** a 1–5 sentence summary of the whole branch, then the bullets from its commits gathered into one list per section, with duplicates removed.

```text
<1–5 sentences: what this branch delivers and why.>

**Features:**
- <plain-language bullet>

**Fixes:**
- <plain-language bullet>
```

## Writing rules for commits and pull requests

These carry over from the team's git specs (`code-guides-git-specs`):

- Include only the sections that have content. A fix-only commit has **Fixes:** and no **Features:**.
- Each bullet is one plain-language sentence about what changed and why it matters, not how the code does it.
- No class, method, file or variable names, and no backticks.
- No tests or verification section, no `Co-Authored-By` line, and no "generated by" line.

## Example

A commit on `ft/login-endpoints`:

```text
Adds the employee login flow so staff can sign in with their work email. Depending on the account, they finish with a password or a one-time code.

**Features:**
- Employees can sign in with their work email and password
- Employees without a password receive a one-time code by email

**Fixes:**
- Locked accounts now see a clear message instead of a generic error
```

The pull request for that branch:

```text
Title: Merging ft/login-endpoints into dev

Adds the employee login flow, with password and one-time code sign-in. It also makes the error clearer for locked accounts.

**Features:**
- Employees can sign in with their work email and password
- Employees without a password receive a one-time code by email

**Fixes:**
- Locked accounts now see a clear message instead of a generic error
```
